## Metric-style census (cross-engine, chapter-defining)

- **C14.1 (verified)** Six operator engines live under `tu_cmodel/compute/`: `convolution_engine.c` (454 lines), `softmax_engine.c` (503), `attention_engine.c` (607), `normalization_engine.c` (441), `pooling_engine.c` (291), `elementwise_pipeline.c` (297); plus `pipeline_controller.c` (469). All seven archive members are present in `libtucmodel.a` (bare names verified via `ar t`).
- **C14.2 (verified)** Engine return values span four distinct metric styles: (a) softmax/norm return **SRAM stall cycles** (`uint64_t`, `UINT64_MAX` on invalid desc); (b) elementwise returns a **post-hoc bandwidth stall estimate** from a different accounting path; (c) pooling returns an **analytical cycle count** (`int64_t`); (d) attention fills a **stats struct** (`dma_bytes/mma_tiles/mma_flops/compute_cycles/dma_cycles/total_cycles/utilization`) and returns 0/-1 status. These are heterogeneous cycle domains; summing them into a total latency is unsupported (fidelity-matrix "Compute engines" row).
- **C14.3 (verified)** SRAM stall sources differ structurally: softmax counts `tu_sram_read` + `tu_sram_write` returns (both); normalization's `sram_load_floats` **discards the read return** (`uint64_t s = 0;` never assigned) while its store path counts writes; elementwise bypasses `tu_sram_read/write` entirely (raw pointers) and accounts `words_available` post-hoc, labeling every served word and every stall as *write* events, and calling `tu_sram_advance_cycle(sram, elem_count)` (which refills bandwidth) before accounting. For the identical 40-element in-place workload on a default region (32 banks × 4 B, 1 word/cycle, penalty 2): softmax returns **96**, norm returns **80**, elementwise returns **40** (hand-derived from `sram_bw_consume` + `tu_sram_bank_index=(addr/4)%32`; reproduced in probe).
- **C14.4 (verified)** `tu_sram_read/write` copy `bank_width` (4) bytes regardless of element width; `tu_sram_bank_index = (addr/bank_width) % bank_count` (tu_sram.h:115).
- **C14.5 (verified)** Conv's cycle surface is a separate analytical API `tu_conv_estimate_cycles(desc, pe_rows, pe_cols)`: `im2col = C·H·W·4/32` + `Σ_groups mt·nt·kt·(2·pe_cols+pe_cols)` + `K·im2col_n` (pinned equation; probe value for the named case: **69**).
- **C14.6 (verified)** Pooling returns `total_cycles = Σ_batch,channel (spatial_out·kh·kw·ops_per_elem) + kh` (drain) — an analytical estimate, not measured; `ops_per_elem` is 1 for max and 2 for average (verified in source and by probe: 4×4→2×2 max **18**, avg **34**).

## Attention engine (composition + known defect)

- **C14.7 (verified)** Attention is the only engine that composes others: it calls the pluggable dataflow MMA, the elementwise pipeline (scale/mask-add), and the softmax engine (standard mode, in-place), with FP16 host tensors and tiled SRAM staging.
- **C14.8 (verified/qualified)** The attention test suite at the pin never passes 9/9: rc=1 in every build, with **6–8/9** passed depending on the build. At the mid-audit build the failing test was `test_scale` (8/9; "Scale differentiation (0.5 vs 2.0)": same output for different scales, err=0.000000); a rebuild under a different disposable work path observed 7/9 (`test_deterministic_small` + `test_causal` failing); the first canonical run observed 6/9 (`test_deterministic_small`, `test_causal`, and `test_scale` all failing). The exact failing subset is UB-dependent (C14.10) — the chapter and its gates target the invariants (rc=1, at least one FAIL line, never 9/9), never a specific failing test or count.
- **C14.9 (verified)** The failure root cause is an SRAM access-width defect, not scale invariance: `fp32_to_fp16_in_sram` and `transpose_fp16_in_sram` use `tu_sram_read/write` (4-byte copies) on 2-byte FP16 values. The in-place FP32→FP16 conversion loop (reverse order, `dst=offset+idx*2`) overwrites the high byte of each previously converted element with 2 garbage bytes. Isolated reproduction: converting `[1..6]` FP32 in place yields `[0,0,0,0,0,0]` (probe `ATTN_CONV_CORRUPT`).
- **C14.10 (verified/qualified)** Differential check vs a naive FP32 golden: engine output max error observed at ≈0.53–0.68 for M=2,N=3,d=8 and ≈0.63 for M=4,N=4,d=8 with pseudo-random FP16 Q/K/V (suite tolerance is 0.25–0.35). The exact corrupted magnitudes are **UB-dependent** (the 4-byte SRAM copies read stack garbage; values vary across builds) — the chapter gates the robust properties (deviation ≫ tolerance; outputs byte-identical across scales), not the magnitudes. The M=1,N=1,d=2 case matches the golden exactly (single P element — no adjacent element to corrupt).
- **C14.11 (verified)** Attention stats are deterministic at the pin for a fixed workload on fresh state: tiny case (M=1,N=1,d=2, scale 1.0) returns `dma=16 B, tiles=2, flops=8, compute=145, dma=2, total=147, util=0.9864` (probe-verified; differs from a back-to-back second execute on the same global state, which inherits exhausted SRAM bank budgets — `dma_bytes`/`tiles`/`flops` are hand-derivable: Q 4 + K 4 + V 4 + O-out 4 = 16; `mma_flops = 2·MACs` with MACs = 1·1·2 + 1·2·1 = 4 → 8). Hand-derivation of compute_cycles = transpose 4 + ew-scale 2 + softmax 4 + fp32→fp16 4 + MMA1 66 + MMA2 65 = 145, where each MMA = fill `pipeline_depth·tile_n` = 2·16 = 32 + execute `k_count` (2 / 1) + drain 32 (WS plugin, pinned equations); dma_cycles = 2 (S zero-init stalls on bank 0 after the O zero-init consumed it; O zero-init hits fresh banks).
- **C14.12 (verified)** Auto-tiling caps tile sizes to sequence lengths **before** aligning up to PE multiples and forcing a `pe_rows/pe_cols` minimum; for M=2, tile_m is logged as 16 (the cap is undone by the alignment, `tu_attention_auto_tile`), though execution counts are re-capped per tile.
- **C14.13 (qualified)** The engine checks SRAM fit using the *aligned* tile sizes (`tile_m·tile_n` FP16 for P, plus FP32 S and O tiles) against the runtime-config SRAM capacities (defaults: W 128 KB, A 64 KB, O 64 KB); for small sequences the FP32 S tile (q_count·kv_count·4 B) and the O tile can be adjacent in the O-buffer with the P conversion in between; correctness of the layout is functional-order dependent and the defect in C14.9 breaks it.

## Functional engines (exact probe values)

- **C14.14 (verified)** Softmax (standard, two-pass, `softmax_row_two_pass`): max-shift, `expf`, double-precision sum, uniform output when sum == 0. Row of four zeros → `[0.25, 0.25, 0.25, 0.25]`, max_out 0.0, returned stalls **8** (4 loads served on fresh banks, 4 stores stall × 2). 40-element census row returns **96**. Invalid desc → `UINT64_MAX` (test-probe verified).
- **C14.15 (verified)** Normalization: LayerNorm two-pass (`mean=Σx/N`, `var=Σ(x−mean)²/N`, `y=(x−mean)/√(var+ε)·γ+β`); RMSNorm (`rms2=Σx²/N`, `y=x/√(rms2+ε)·γ`, β ignored). `[1,1,1,1]`, ε=1e-5: LayerNorm → `[0,0,0,0]`, mean_out 1.0, var_out 0.0, stalls **8**; RMSNorm → `0.999995` each, var_out 1.0. 40-element census returns **80** (load stalls discarded).
- **C14.16 (verified)** Elementwise fused chains (≤8 ops, 17 opcodes incl. GELU tanh-approx `0.5x(1+tanh(0.7978845608(x+0.044715x³)))`, SiLU `x/(1+e^{−x})`, binary ADD/MUL/SUB/DIV/MIN/MAX; DIV by zero → 0.0; SQRT(x<0) → 0.0; LOG(x≤0) → −inf). Chain `[ADD 2, RELU]` on `[-3,1,5]` → `[0,3,7]`, stalls **2**; 40-element census returns **40**.
- **C14.17 (verified)** Pooling: MaxPool ignores padded windows unless the whole window is padding (then `pad_value`); AvgPool divides by the count of **valid** elements. 4×4 max 2×2/2 → `[6,8;14,16]`; avg → `[3.5,5.5;11.5,13.5]`; returns cycles **18** / **34**. Validation: `elem_size` 1..8, `pool_type < TU_POOL_COUNT`, regions non-null.
- **C14.18 (verified)** Convolution: `tu_conv_compute_dims` derives OH/OW and im2col rows/cols; direct FP32 NCHW/NHWC references and im2col+GEMM pipeline agree for the probe case (all-ones 1×3×3 input, 2×3×1×1 kernel, weight[k][c]=c+1 → output 6.0 everywhere); `estimate_cycles` = **69** for that case.
- **C14.19 (verified)** Pipeline controller: bounded tile slots (depth 1–8), stages IDLE/DMA_PRELOAD/COMPUTE/DMA_STORE/DONE; `sequential_total` accumulates load+compute+store per tile (load/store default **1** cycle when no descriptor). Depth-1 scenario: `sequential_total=204, saved=0, stalls=0` (2 tiles × (1+100+1)). Depth-2 with 3200-B load descriptors (load window 100 cycles) and compute 100: `sequential_total=402, saved=200` — both preload→compute transitions occur while `active_count==2` and credit the 100-cycle load window (`overlapped_load_cycles`), i.e. 2×100; backpressure returns −1 after retries and counts a stall. **configured-but-ineffective state**: descriptor-free tiles accrue zero overlap even with `enable_load_overlap=true` — the overlap credit is proportional to a tile's load-descriptor byte count, so the config flag alone does nothing.

## Fidelity and boundary claims

- **C14.23 (verified)** No engine metric at the pin is calibrated; all cycle/stall/cycle-count values come from the pinned equations (ch13 analog: estimator outputs are analytical). Nothing here is a measured latency or hardware claim.
- **C14.24 (verified)** There is no configured-runtime dispatch path that selects an operator engine from configuration or executes conv/softmax/attention/pooling/pipeline through `tu_config` → runtime; the elementwise queue command is the only config-adjacent integration (still a direct API call, not engine selection by config field).
- **C14.25 (qualified)** The chapter's functional claims cover the named probe/tests values and value domains; arbitrary-input FP16 attention correctness is **rejected** as a claim at this pin (C14.9/C14.10).
- **C14.26 (verified)** Declaration/configured-state distinction holds: engine descriptors are caller-constructed (declared state); `g_tu.rt_cfg` (pe_rows/cols, SRAM sizes, dataflow) is the configured state attention reads; no engine reads a `tu_config_t` field.
